# Agent Note: H6 NCM 接收端的可选短包填充

Status: implemented

## Problem

code31实车21:25:15记录 block=3584 buffered=5156 next=4e,43,4d,48。块末紧接下一合法NCMH块头，但接收器强制在每个512倍数块后读一个零字节，将正常链路判断损坏并主动断开；自动重连又受到原车音频/HID回绑阻断。

## Decision

按NTB头声明的长度完成严格解析并立即交付帧。仅在512倍数块后的边界允许一个可选零字节；无零字节时必须匹配下一NCMH头的已到达前缀，再沿原有严格NTB16/NDP/数据报校验继续。可选填充状态跨读块保留，不依赖UsbRequest完成边界。非法前缀、损坏表/范围及缓存/帧队列溢出保持终止语义。发送端填充格式不改。code32先在实际安装源码的隔离副本构建；2026-10-08按用户指定同步到主项目 `/Users/lanyu/IdeaProjects/DiPlay`。

## Alternatives considered

- 继续强制零字节能保持既有假设，但合法NCMH的四字节实车证据直接反驳这个假设。
- 忽略所有块尾未知字节或搜索下一NCMH能避免断线，但会隐瞒损坏和丢包，不采用。
- 只更换数据线可解决接触相关真实枚举失败，但不能消除对合法下一块头的软件拒绝，两个问题分开处理。

## Testing

复现3584+1572=5156字节无填充流；验证512/1024/3584/16384块的有/无填充及下一头0–12字节分割。合法完整块不等待额外字节；畸形填充/后继头/数据报仍终止会话。shared362/common156共518项，517通过、1项既有跳过，0失败/错误；lint、跨模块API23、同步清单、公有树、v1/v2签名及与code31认证资产逐字节对比通过。code32 APK SHA256为28dbbbb463b4de487c67d6557c0deab6eead2d1b26924381782bbaead8b0f4f1。实车AirPlay会话从21:41:41持续采集到21:50:01，约8分20秒；PID12391窗口内未见NCM reassembly failed或USB requeue failed，末尾仍有视频接收和协议交互。用户确认稳定性明显改善，但音乐仍在手机播放。此样本不代替长时间、ACC及接触稳定性验收。音频转到新会话排查，本会话停止实时采集，保留code32且未主动断开CarPlay。原始实车证据保留在旧工作目录的私有日志中；主项目交接见[音频同步记录](../../../../docs/android_6/AUDIO_2026-10-08.md)。

## Consequences

合法块边界不再触发伪损坏和重连，保持缓存/队列限制及严格块内校验；维护一个跨读块的可选填充状态。发送端格式、接口释放与恢复权限均不变。实际USB线缆或端口仍可能产生-71，软件修复不消除硬件问题；音频根因未确定，不改媒体路由或麦克风。主项目纳入解析器和对应回归，原始隔离副本及code32回滚包保留；[静音输入候选](2026-10-07-h6-silent-audio-input.md)扩展音频协商排查，不改变本篇NCM决定。
